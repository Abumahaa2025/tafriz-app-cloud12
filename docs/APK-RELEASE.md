# رفع نسخة APK جديدة بأمان

الملف المنشور للمستخدمين هو `public/downloads/Tafriz.apk`، وينزّلونه من
`https://tafriz-app-cloud12.vercel.app/install.html`.

التطبيق **ليس** نسخة Capacitor — هو غلاف **TWA** (Trusted Web Activity) اسم حزمته
`com.tafriz.app`، وكل شاشاته تُحمَّل من الموقع نفسه. يعني: تحديثات الواجهة والفرز
والتشيك تصل للمستخدم من نشرة Vercel مباشرة، وما يحتاج APK جديد إلا لو تغيّر شيء
داخل الغلاف نفسه (الأيقونة، اسم الحزمة، الأذونات، رابط الموقع).

## ليش النسخة السابقة كانت تعطي «لم يتم تثبيت التطبيق»

الحزمة اللي كانت منشورة اتفكّت وأُعيد ضغطها بأداة zip عامة ثم وُقّعت بـ `jarsigner`.
هذا كسر ثلاثة شروط إلزامية في أندرويد 11 فأحدث دفعة واحدة:

| الشرط | حالة النسخة المكسورة | النتيجة على الجوال |
| --- | --- | --- |
| توقيع APK Signature Scheme v2 فأعلى (إلزامي لـ `targetSdk` 30+) | توقيع v1 فقط | يُرفض التثبيت فورًا |
| `resources.arsc` مخزّن بدون ضغط ومحاذى 4 بايت (إلزامي لـ `targetSdk` 30+) | مضغوط | يُرفض التثبيت فورًا |
| أسماء الملفات داخل الحزمة تستخدم `/` | 443 ملفًا بـ `\` | لا يجد `res/` فتضيع الأيقونة والواجهات |

`targetSdk` في هذه الحزمة هو 35، فكل الشروط الثلاثة تنطبق عليها.

## الفحص قبل أي رفع

```bash
npm run verify:apk
```

يفشل الأمر ويمنع الرفع إذا رجع أي شرط من الثلاثة للخطأ. شغّله دائمًا بعد أي تعديل
على `public/downloads/Tafriz.apk`.

## بناء وتوقيع حزمة جديدة

لا تفك ضغط الـ APK وتعيد ضغطه أبدًا. ابنِ من المصدر ثم وقّع بـ `apksigner` (وليس
`jarsigner`، لأن `jarsigner` يعرف توقيع v1 فقط):

```bash
# 1) محاذاة (لازم قبل التوقيع، لا بعده)
zipalign -p -f 4 app-release-unsigned.apk app-aligned.apk

# 2) توقيع بكل المخططات
apksigner sign \
  --ks tafriz-release.keystore --ks-key-alias tafriz \
  --min-sdk-version 23 \
  --v1-signing-enabled true --v2-signing-enabled true --v3-signing-enabled true \
  --out public/downloads/Tafriz.apk app-aligned.apk

# 3) تأكيد
apksigner verify --verbose --print-certs public/downloads/Tafriz.apk
npm run verify:apk
```

`apksigner` و `zipalign` يجيان مع Android SDK Build Tools.

## مفتاح التوقيع

النسخة الحالية موقّعة بمفتاح جديد، بصمته SHA-256:

```
92:79:6C:5C:12:B4:5B:37:83:A9:13:CF:87:52:9F:84:0C:EE:AD:E8:2C:CA:34:E8:C0:0A:B9:40:A7:F2:53:32
```

هذه البصمة مضافة في `public/.well-known/assetlinks.json` مع البصمات القديمة — لا
تحذف القديمة حتى لا تنكسر أي نسخة مثبّتة سابقًا.

قواعد ثابتة:

- **لا ترفع ملف الـ keystore للمستودع** — المستودع عام، وأي أحد يحصل عليه يقدر
  يوقّع تحديثًا خبيثًا يُثبَّت فوق تطبيقك. خزّنه في GitHub Secrets.
- أي حزمة جديدة لازم تُوقَّع **بنفس المفتاح**، وإلا ما تقدر تُثبَّت كتحديث فوق
  المثبّتة ولازم المستخدم يحذف القديمة أولًا.
- ارفع `versionCode` مع كل نسخة (الحالية `2`)، وإلا أندرويد يرفض تثبيتها كتحديث.

## «الملف نزل كمستند وليس تطبيق»

هذه الشكوى ما لها علاقة بالحزمة نفسها ولا بالسيرفر. الحزمة تُقدَّم بنوع
`application/vnd.android.package-archive` مع `Content-Disposition: attachment`،
والمشكلة كلها في **من ينزّل الملف**:

| البيئة | ما يصير | ما تفعله `install.html` |
| --- | --- | --- |
| Chrome على أندرويد | التنزيل يصل لمثبّت الحِزم ويُثبَّت | تعرض زر APK (المسار الأساسي) |
| متصفح مدمج داخل واتساب/تيليجرام/إنستقرام | الملف يُحفظ كمستند ولا يصل لمثبّت الحِزم | تحجب زر APK وتفتح Chrome عبر رابط `intent://` |
| آيفون / آيباد | iOS يحفظ الـ APK في «الملفات» كمستند دائمًا | تخفي زر APK وتشرح «إضافة إلى الشاشة الرئيسية» |
| كمبيوتر | الملف يبقى ملفًا على القرص | تخفي زر APK وتعطي رابطًا يُرسل للجوال |

الصفحة كذلك تعرض زر «تثبيت مباشر بدون تنزيل ملف» عندما يسمح المتصفح
(`beforeinstallprompt`)، وهذا أضمن مسار لمن يفشل عنده تثبيت APK.

ترويسات `/downloads/` مربوطة بمسار الملف بالاسم الكامل `/downloads/Tafriz.apk`،
حتى لا يخرج أي رد 404 داخل المجلد بترويسة `Content-Disposition` توهم المتصفح أنه
ينزّل `Tafriz.apk` بينما هو نص خطأ قصير — كان هذا يُنتج «مستندًا» باسم الحزمة.

## حماية الرابط المباشر من «المستند»

الحماية السابقة كانت في `install.html` فقط، فهي تعمل لمن يفتح **الصفحة**. لكن الشكوى
تكرّرت لأن الذي يُرسَل عادةً هو رابط **الملف** `‎/downloads/Tafriz.apk` مباشرة، وحينها
لا شيء يحمي المستخدم: المتصفح المدمج ينزّله كمستند فورًا.

لذلك صار التحقّق على مستوى السيرفر في `vercel.json`، على ترويسة `user-agent` للطلب
نفسه:

| البيئة الطالبة | ما يحدث لرابط الملف المباشر |
| --- | --- |
| متصفح مدمج (`; wv)`، FBAN/FBAV، Instagram، Line، MicroMessenger، Snapchat، TikTok، Twitter) | تحويل 307 إلى `‎/install.html?src=inapp` |
| iOS (iPhone/iPad/iPod) | تحويل 307 إلى `‎/install.html?src=ios` |
| Chrome أندرويد، `AndroidDownloadManager`، كمبيوتر | **الملف كما هو** — لم يتغيّر شيء |

القاعدة تفشل «مفتوحة»: أي `user-agent` لا يطابق الأنماط أعلاه يستلم الحزمة كالسابق،
فلا يوجد مسار تثبيت قائم يُكسر. و `install.html` تقرأ `src` وتعرض البطاقة الصحيحة
مباشرة بدل الاعتماد على استنتاجها وحده.

رابط قصير للمشاركة: `https://tafriz-app-cloud12.vercel.app/app` يحوّل لصفحة التثبيت.
**أرسل هذا الرابط** بدل رابط الملف.

## ملاحظة مفتوحة: إذن الإنترنت

الحزمة ما فيها `android.permission.INTERNET`. فُحصت الحزمة بـ `aapt` وتبيّن أن
`FALLBACK_STRATEGY` فيها = `customtabs` لا `webview`، أي أن `WebViewFallbackActivity`
معلَنة لكن غير مستخدمة: كل المسارات تفتح المحتوى داخل المتصفح (TWA أو Custom Tab)،
والشبكة تجري في عملية المتصفح لا في عملية التطبيق. فنقص الإذن **ليس** سبب «التطبيق
لا يفتح» — يبقى نقصًا يُصحَّح للسلامة عند أول إعادة بناء بـ Bubblewrap، لا أكثر.

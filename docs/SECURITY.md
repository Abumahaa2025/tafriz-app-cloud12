# نموذج الأمان في تطبيق الفرز

## أولًا: ما الذي لا يمكن إخفاؤه

"الفرز" تطبيق ويب. كود الواجهة يُنزَّل كاملًا على جهاز كل مستخدم، وأي أحد يقدر
يفتح أدوات المطوّر ويقرأه. **لا توجد طريقة تمنع الهندسة العكسية للواجهة** — لا
تشفير ولا تشويش (obfuscation) يغيّر هذي الحقيقة، لأن المتصفح لازم يفهم الكود
حتى ينفّذه.

فالحماية ما تكون بإخفاء الكود، بل بأن **الكود المكشوف لا يحوي شيئًا يستحق
الإخفاء**، وأن **كل قرار حسّاس يُتخذ على الخادم أو داخل قاعدة البيانات** لا في
المتصفح.

هذا المبدأ مطبّق هنا على ثلاث طبقات:

## الطبقة الأولى: لا سر يصل للمتصفح

| المفتاح | أين يعيش | لو انكشف |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | المتصفح | لا شيء — عنوان عام |
| `VITE_SUPABASE_ANON_KEY` | المتصفح | لا شيء — مفتاح عام مصمَّم للنشر، وRLS هي الحماية |
| `VITE_SENTRY_DSN` | المتصفح | لا شيء حسّاس — DSN عام لمشروع Sentry |
| `SUPABASE_SERVICE_ROLE_KEY` | الخادم فقط | **كارثة** — يتجاوز RLS ويقرأ ويعدّل كل بيانات المشتركين |
| `ANTHROPIC_API_KEY` | الخادم فقط | فاتورة على حسابك |
| `GEMINI_API_KEY` | الخادم فقط | فاتورة على حسابك (Gemini + Google Maps grounding) |
| `SENTRY_AUTH_TOKEN` | CI/الخادم فقط إن لزم | يرفع sourcemaps — **لا يُوضع في Git ولا في `VITE_`** |

القاعدة الحاسمة: **Vite يستبدل كل متغيّر يبدأ بـ `VITE_` بقيمته نصًّا داخل حزمة
الجافاسكربت وقت البناء.** فوضع سر في متغيّر `VITE_` = نشره على الإنترنت، حتى لو
كان الملف الأصلي محميًا. المفاتيح السرية تُقرأ فقط داخل `api/` عبر
`lib/api/env.ts`، وهذي الملفات تعمل على الخادم ولا تُرسل للمتصفح أبدًا.

للتأكد أن الحزمة المنشورة نظيفة:

```bash
npm run build
grep -rE 'sb_secret_|sk-ant-|AIza|SERVICE_ROLE|GEMINI_API_KEY' dist/ && echo "تسريب!" || echo "نظيفة"
```

كذلك لا تُنشَر خرائط المصدر (source maps) في الإنتاج — إعداد Vite الافتراضي
`build.sourcemap: false`، فلا يُكشف الكود الأصلي بأسماء متغيّراته وتعليقاته.

## الطبقة الثانية: الصلاحيات تُفرض في قاعدة البيانات

حتى لو كتب مهاجم طلباته بنفسه وتجاهل الواجهة تمامًا، الحماية باقية:

- **RLS مفعّلة على كل جدول** (٨ جداول). المستخدم يقرأ صفوفه هو فقط، والمالك
  وحده يقرأ الكل.
- **تريغر `assign_owner_on_signup`**: أي حساب جديد يدخل `pending` إجباريًا، حتى
  لو أرسل الطلب `is_owner: true`.
- **تريغر `protect_profile_fields`**: أي محاولة من غير المالك لتغيير `status`
  أو `is_owner` أو بيانات الباقة تُعاد لقيمتها القديمة داخل قاعدة البيانات.

يعني: تعديل كود الواجهة ما يمنح المهاجم شيئًا — القرار ليس عند المتصفح.

### قاعدة على `api/auth-register`

`/api/auth-register` هي **النقطة الوحيدة المفتوحة بلا تحقق من الهوية** — أي أحد
على الإنترنت يقدر يناديها، وهي تحمل مفتاح `service_role`. لذلك:

> **ممنوع أن تعدّل هذي النقطة أي شيء في حساب موجود مسبقًا.**

سابقًا كانت، إذا وجدت المعرّف موجودًا، تستدعي:

```ts
admin.auth.admin.updateUserById(userId, { password, email_confirm: true })
```

فتستبدل كلمة مرور الحساب القائم بما أرسله المنادي. ولأن `OWNER_IDENTIFIER`
مكتوب داخل حزمة الجافاسكربت العامة (لأنه في `src/`)، كان أي شخص يقرأ الحزمة
ويرسل طلبًا واحدًا برقم المالك وكلمة مرور من اختياره، ثم يدخل مالكًا. ونفس
الشيء ينطبق على حساب أي مشترك يُعرف رقمه.

الآن: الحساب القائم لا تُلمس كلمة مروره ولا بروفايله. يُرفع فقط `email_confirm`
حتى لا يبقى حساب قديم غير مؤكَّد عاجزًا عن الدخول، ثم يقرر Supabase Auth نفسه:
كلمة المرور الصحيحة تدخل، والخاطئة تُرفض. كلمة المرور تُكتب في حالة واحدة فقط
وهي `createUser` لحساب جديد تمامًا.

عند أي تعديل مستقبلي على هذي النقطة، تأكد أن الطلبات الصادرة لحساب قائم لا تحوي
`password` إطلاقًا.

للتحقق:

```bash
npm run verify:db -- <url> <anon-key>
```

## الطبقة الثالثة: الأخطاء لا تشرح النظام للمهاجم

رسالة الخطأ التفصيلية هدية مجانية لمن يحاول فهم نظامك. نص خطأ Postgres واحد
يكشف اسم الجدول والعمود والقيد وأحيانًا اسم سياسة RLS.

كل الدوال في `api/` ترد عبر `lib/api/errors.ts`، وقاعدته:

> التفاصيل الداخلية تروح للسجل، والمستخدم يشوف نصًا كتبناه نحن.

عمليًا:

- **لا يُرجَع `error.message`** من قاعدة البيانات ولا من أي مزوّد خارجي للمتصفح.
- كل رد خطأ = رمز ثابت (`error`) + رسالة عربية مكتوبة في هذا المستودع
  (`message`) + معرّف طلب قصير (`requestId`).
- التفاصيل الكاملة تُكتب في Vercel ▸ Logs مربوطة بنفس `requestId`، فتقدر
  تشخّص أي بلاغ من المستخدم بدون ما يشوف هو شيئًا.
- **حتى السجلات تُنقّى**: `redactSecrets` يستبدل أي نص يشبه مفتاحًا
  (`sb_secret_`, `sk-ant-`, JWT, `Bearer …`) بـ `[REDACTED]` قبل الكتابة، لأن
  سجلات الاستضافة يقرأها كل من له وصول للوحة.

مقارنة عملية على نفس الخطأ:

```
قبل:  duplicate key value violates unique constraint "activation_codes_pkey"
      DETAIL: Key (code)=(TFZ-477163) already exists.

بعد:  { "error": "code_insert_failed",
        "message": "تعذّر تنفيذ العملية. أعد المحاولة، وإن تكرر تواصل مع الإدارة.",
        "requestId": "8f2a1c40" }
```

الرد الثاني ما يذكر Postgres ولا اسم جدول ولا رمزًا موجودًا فعلًا في النظام.

## حدود إضافية

- `api/recognize-plate` يرفض أي ملف أكبر من 8 ميجابايت وأي نوع غير صورة، حتى لا
  يستنزف أحد ذاكرة الدالة بطلب ضخم.
- **حد طلبات (rate limit)** في ذاكرة الدالة عبر `lib/api/rate-limit.ts`
  (أفضل جهد لكل instance على Vercel، وليس موزّعًا عالميًا):

  | المسار | الحد التقريبي |
  | --- | --- |
  | `/api/auth-register` | 10 / 15 دقيقة لكل IP |
  | `/api/access-control` | 60 / دقيقة لكل مستخدم؛ تفعيل الرمز 20 / 15 دقيقة |
  | `/api/recognize-plate` | 20 / ساعة لكل مستخدم موافق |
  | `/api/maps-assist` | 60 / دقيقة لكل مستخدم موافق |

  عند التجاوز: `429` + `Retry-After`. للحد العالمي استخدم WAF على النطاق.
- تحقّق مدخلات أضيق: طول المعرّف/كلمة المرور في التسجيل، أيام الباقة، أسماء
  الباقات، معرّفات UUID، وطول ردود الملاحظات.
- **ترويسات أمنية آمنة للخرائط** في `vercel.json` (بدون CSP مُلزم):
  `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
  `Permissions-Policy` (geolocation/microphone/camera للذات فقط).
  لا نضع Content-Security-Policy إلزامية حتى لا تُكسر بلاطات/سكربتات الخرائط.
- للتحقق من RLS على مشروع الإنتاج شغّل `supabase/verify-rls.sql` من SQL Editor.
- الدوال الخادمية تُفحص بـ `npm run typecheck:api`. قبل ذلك كان `tsconfig.json`
  يغطّي `src/` فقط، فكان مجلد `api/` — وفيه المفتاح السري — بلا أي فحص أنواع.

## قيد إلزامي على استيراد الملفات داخل api/

`package.json` فيه `"type": "module"`، فالملفات التي تنتجها Vercel من `api/`
تعمل كـ **ESM** على Node. وESM يوجب **امتداد `.js` صريحًا** في أي استيراد نسبي:

```ts
import { fail } from "../lib/api/errors.js";   // ✅
import { fail } from "../lib/api/errors";      // ❌ ERR_MODULE_NOT_FOUND وقت التشغيل
```

الاستيراد بدون امتداد يمر في الفحص العادي ويُبنى بنجاح، ثم تسقط الدالة في
الإنتاج بـ `FUNCTION_INVOCATION_FAILED`. لهذا `tsconfig.api.json` مضبوط على
`moduleResolution: "nodenext"` — وحده يرفض الاستيراد الناقص وقت الفحص. **لا
تبدّله بـ `bundler`**، لأن `bundler` يسمح بالاستيراد بدون امتداد فيرجع الخطأ
مختبئًا حتى النشر.

هذا القيد لا ينطبق على `src/`: حزمة الواجهة يبنيها Vite ويحلّ الامتدادات بنفسه.

## قبل كل نشر

```bash
npm run typecheck:api   # الدوال الخادمية (يمسك أخطاء الاستيراد أعلاه)
npm run build           # الواجهة
npm run verify:db -- <url> <anon-key>
npm run verify:apk
```

للتحقق الكامل من أن الدوال تُحمَّل فعلًا كما ستُحمَّل على Vercel (وليس فقط أنها
تُفحص بنجاح)، ابنِ نقاط الدخول بـ `@vercel/node` ثم استورد الناتج وشغّله على
Node — الفحص وحده لا يكشف `ERR_MODULE_NOT_FOUND`.
